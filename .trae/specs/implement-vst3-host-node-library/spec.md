# nst3 — VST3 Host for Node.js Spec

## Why
Node.js lacks a production-grade VST3 host library. As a result, JS-based audio applications, server-side DSP pipelines, automated plugin testing, and DAW-like tooling cannot leverage VST3 — the modern industry-standard plugin format. Existing approaches require per-platform C++ compilation at install time (broken on machines without toolchains) or shelling out to external processes (unacceptable latency and missing parameter/MIDI control). `nst3` closes this gap by shipping prebuilt native binaries through npm so users can `npm install nst3` and immediately load, automate, and process audio through any installed VST3 plugin.

## What Changes
- Build a Node.js native addon package `nst3` using **Rust + napi-rs** (N-API ABI-stable across Node.js 16/18/20/22+).
- Implement a complete VST3 host in pure Rust: minimal COM FFI bindings (no SDK submodule, no bindgen, no libclang), module discovery, factory invocation, audio processing, parameter automation, MIDI I/O, state persistence, and host-application callbacks.
- Expose a TypeScript-friendly API via napi-rs with zero-copy audio buffers (`Float32Array` views), `Buffer` for state blobs, and structured parameter/event objects.
- Distribute via npm with platform-specific optional dependencies: `nst3-darwin-x64`, `nst3-darwin-arm64`, `nst3-win32-x64-msvc`, `nst3-linux-x64-gnu`. Users never compile from source.
- Build matrix via GitHub Actions producing signed Release artifacts consumed by `npm publish`.
- Keep MIT license; no GPL contamination (no `vst3-sys` / `vst3-host` GPL crates).

## Impact
- Affected specs: none (new project, repo currently only has README/LICENSE).
- Affected code: new repository layout — Rust crate `crates/nst3-host` (host core), `crates/nst3-napi` (napi-rs bindings, main npm package), `packages/*` (platform-specific sub-packages auto-generated by `@napi-rs/cli`), `examples/`, `__tests__/`, `.github/workflows/CI.yml`.
- Native binary size: ~2–5 MB per platform.
- Runtime requirement: VST3 plugins installed at standard OS locations or referenced by absolute path.
- Node.js engine requirement: `>=16.17` (Node-API v8).

## ADDED Requirements

### Requirement: Plugin Discovery
The system SHALL provide plugin discovery that scans standard VST3 plugin locations per platform and returns metadata for each found plugin without instantiating the DSP.

Standard locations:
- macOS: `/Library/Audio/Plug-Ins/VST3`, `~/Library/Audio/Plug-Ins/VST3`
- Windows: `C:\Program Files\Common Files\VST3`, `%LOCALAPPDATA%\Programs\Common\VST3`
- Linux: `/usr/lib/vst3`, `/usr/local/lib/vst3`, `~/.vst3`

#### Scenario: Scan default locations
- **WHEN** the user calls `Host.scanDefaultLocations()`
- **THEN** the system returns an array of `PluginInfo` objects, each containing `{ path, name, vendor, version, category, subCategories, sdkVersion, factoryInfo }`

#### Scenario: Scan a specific directory
- **WHEN** the user calls `Host.scanDirectory('/custom/path')`
- **THEN** the system recursively finds `.vst3` bundles/modules and returns `PluginInfo[]`

#### Scenario: Read metadata from a single plugin file
- **WHEN** the user calls `Host.inspectPlugin('/path/to/plugin.vst3')`
- **THEN** the system loads the factory, reads class info, and returns one `PluginInfo` (or array if the file contains multiple plugins) without instantiating components

### Requirement: Plugin Loading & Initialization
The system SHALL load a VST3 plugin module by path, instantiate its `IComponent`, query its `IAudioProcessor`, connect it to its `IEditController` (when separate), and configure the host application context.

#### Scenario: Load plugin with audio config
- **WHEN** the user calls `host.load('/path/plugin.vst3', { sampleRate: 48000, maxBlockSize: 512 })`
- **THEN** the system returns a `PluginInstance` whose audio inputs/outputs are reported via `getInfo()` and which is ready to be activated

#### Scenario: Component/controller connection
- **WHEN** the plugin exposes a separate `IEditController` (created via `IEditController::createInstance` or `IPluginFactory3::createInstance`)
- **THEN** the host connects both via `IConnectionPoint` so parameter changes from the controller propagate to the processor and vice-versa

#### Scenario: Host application context
- **WHEN** the component calls `IComponent::queryInterface(IHostApplication)`
- **THEN** the host returns a valid `IHostApplication` that responds to `getName` with `"Node.js VST3 Host"` and supports query of standard VST3 class IDs (e.g., `IMessage`, `IAttributeList`)

### Requirement: Audio Processing
The system SHALL process audio through the plugin with zero-copy buffer handling, supporting configurable channel counts, sample rates, and block sizes.

#### Scenario: Process a block of audio
- **WHEN** the user calls `plugin.process({ inputs: [left, right], outputs: [outLeft, outRight], numSamples: 512 })`
- **THEN** the plugin's `IAudioProcessor::process` is called with a `ProcessData` containing the supplied audio buffers, parameter changes, and event list, and the `outputs` Float32Arrays are filled with the processed audio

#### Scenario: Activate/deactivate processing
- **WHEN** the user calls `plugin.setActive(true)`
- **THEN** `IAudioProcessor::setActive(true)` is called with the configured `ProcessSetup` (sample rate, block size, sample format Float32, processing real-time)
- **WHEN** the user calls `plugin.setActive(false)`
- **THEN** `IAudioProcessor::setActive(false)` is called to release resources

#### Scenario: Set processing state
- **WHEN** the user calls `plugin.setProcessing(true)` before processing
- **THEN** `IAudioProcessor::setProcessing(true)` is called; subsequent `process` calls are valid
- **WHEN** the user calls `plugin.setProcessing(false)` after processing
- **THEN** `IAudioProcessor::setProcessing(false)` is called

#### Scenario: Latency reporting
- **WHEN** the plugin reports a non-zero `initialDelay` after `setActive(true)`
- **THEN** `plugin.getLatency()` returns the latency in samples so the caller can apply delay compensation

#### Scenario: Speaker arrangement negotiation
- **WHEN** the plugin is loaded
- **THEN** the host queries `IAudioProcessor::getBusArrangement` for inputs and outputs and sets a default stereo arrangement when the plugin supports it

### Requirement: Parameter Management
The system SHALL expose complete parameter read/write, info queries, and parameter change automation, normalized to `[0,1]` per the VST3 spec.

#### Scenario: List parameters
- **WHEN** the user calls `plugin.getParameterInfo(index)`
- **THEN** the system returns a `ParameterInfo` object `{ id, title, shortTitle, units, stepCount, defaultNormalizedValue, unitId, flags }` where `flags` is a numeric bitmask of `ParameterFlags` (canAutomate, isReadOnly, isWrapAround, isList, isHidden, isBypass)

#### Scenario: Read parameter value
- **WHEN** the user calls `plugin.getParameter(id)`
- **THEN** the system returns the current normalized value from the controller (`IEditController::getParamNormalized`)

#### Scenario: Set parameter value
- **WHEN** the user calls `plugin.setParameter(id, 0.5)`
- **THEN** the system sets the value on the controller (`IEditController::setParamNormalized`), starts a parameter change on the processor queue (`IParamValueQueue::addPoint`), and triggers `IComponentHandler::performEdit` if a host-edit gesture is in progress

#### Scenario: Batch parameter set
- **WHEN** the user calls `plugin.setParameters([{id: 0, value: 0.5}, {id: 1, value: 0.75}])`
- **THEN** the system applies all changes atomically before the next `process` call

#### Scenario: Format parameter display
- **WHEN** the user calls `plugin.formatParameter(id, value)`
- **THEN** the system calls `IEditController::getParamStringByValue` and returns the plugin's own display string (e.g., `"8.2 kHz"`)

### Requirement: MIDI & Event Handling
The system SHALL accept MIDI events (note on/off, CC, pitch bend, program change, poly aftertouch, channel pressure) and SysEx, and queue them for the next `process` call via `IEventList`.

#### Scenario: Add a MIDI note
- **WHEN** the user calls `plugin.addMidiEvent({ type: 'noteOn', channel: 0, note: 60, velocity: 100, sampleOffset: 0 })`
- **THEN** a corresponding `Event` is added to the internal event list and will be passed to the plugin on the next `process` call

#### Scenario: Add raw MIDI bytes
- **WHEN** the user calls `plugin.addMidiBytes(sampleOffset, [0x90, 0x3C, 0x64])`
- **THEN** the system parses the bytes per VST3 MIDI mapping and adds the equivalent `Event`

#### Scenario: Capture plugin MIDI output
- **WHEN** the plugin emits events during `process` (via the output `IEventList`)
- **THEN** `plugin.takeOutputEvents()` returns an array of `MidiEvent` and clears the internal output queue

#### Scenario: Clear events between blocks
- **WHEN** the user calls `plugin.clearEvents()`
- **THEN** the input event list is cleared without being processed

### Requirement: State Persistence
The system SHALL save and restore the plugin's full state (component state and optional controller state) as a `Buffer` blob.

#### Scenario: Save state
- **WHEN** the user calls `plugin.saveState()`
- **THEN** the system calls `IComponent::getState(IBStream)` and returns a `Buffer` containing the serialized state

#### Scenario: Load state
- **WHEN** the user calls `plugin.loadState(buffer)`
- **THEN** the system calls `IComponent::setState(IBStream)` and `IEditController::setComponentState(IBStream)` (when a controller exists) to restore the plugin state

#### Scenario: Round-trip preserves state
- **WHEN** the user saves state, modifies parameters, then loads the saved state
- **THEN** the parameters and internal state are restored to their saved values

### Requirement: Host Application Support
The system SHALL implement `IHostApplication`, `IComponentHandler`, `IComponentHandler2`, `IComponentHandler3`, and `IHostApplication` so the plugin can communicate with the host.

#### Scenario: Parameter edit gesture
- **WHEN** the plugin's controller calls `IComponentHandler::beginEdit(id)`
- **THEN** the host tracks the active gesture
- **WHEN** `performEdit(id, value)` is called during the gesture
- **THEN** the host updates the parameter queue
- **WHEN** `endEdit(id)` is called
- **THEN** the host finalizes the gesture

#### Scenario: Request parameter re-sync
- **WHEN** the plugin calls `IComponentHandler::restartComponent(kLatencyChanged | kParamValuesChanged)`
- **THEN** the host re-reads the latency and parameter values and emits a JS event `restart` with the restart flags

#### Scenario: Plugin-to-controller message
- **WHEN** the component sends a `IMessage` via `IConnectionPoint::notify`
- **THEN** the host routes it to the controller's `IConnectionPoint::notify`

### Requirement: Error Handling & Resource Management
The system SHALL handle errors gracefully, leak no native resources, and provide clear JS errors with VST3-specific context.

#### Scenario: Plugin fails to load
- **WHEN** `host.load('/nonexistent.vst3')` is called
- **THEN** the host throws a JS `Error` with `code: 'VST3_LOAD_FAILED'` and a descriptive message including the path and OS-level error

#### Scenario: Plugin crashes during processing
- **WHEN** the plugin's `process` call segfaults or returns an error code
- **THEN** the host catches the error (Rust panic / non-zero result), marks the plugin as faulted, throws a JS `Error` with `code: 'VST3_PROCESSING_ERROR'`, and subsequent calls throw `VST3_FAULTED`

#### Scenario: Cleanup on dispose
- **WHEN** the user calls `plugin.dispose()` or the `PluginInstance` is garbage collected
- **THEN** the host calls `setProcessing(false)`, `setActive(false)`, releases all COM references, unloads the dynamic library, and frees native buffers

### Requirement: Native Binary Distribution
The system SHALL ship prebuilt native binaries via npm so end users never compile from source.

#### Scenario: Install on supported platform
- **WHEN** a user runs `npm install nst3` on Windows x64, macOS x64, macOS arm64, or Linux x64
- **THEN** the platform-specific optional dependency is installed and `require('nst3')` loads the native binary without compilation

#### Scenario: Unsupported platform fallback
- **WHEN** a user installs on an unsupported platform (e.g., Linux arm64 musl)
- **THEN** `require('nst3')` throws a clear `Error` with `code: 'VST3_PLATFORM_UNSUPPORTED'` listing the supported triples

#### Scenario: GitHub Release assets
- **WHEN** a version is tagged
- **THEN** the CI workflow builds all targets, uploads artifacts to GitHub Releases, and publishes platform-specific packages to npm with the version from the tag

### Requirement: TypeScript API Surface
The system SHALL ship a complete TypeScript declaration file (`index.d.ts`) covering all public classes, methods, structures, and enums.

#### Scenario: Type-safe usage
- **WHEN** a TypeScript user imports `nst3`
- **THEN** they get full types for `Host`, `PluginInstance`, `PluginInfo`, `ParameterInfo`, `MidiEvent`, `ProcessBlock`, `HostOptions`, `LoadOptions`, and enum unions (`ParameterFlags`, `RestartFlags`, `BusType`, `MediaType`, `ControllerBusTypes`, `PluginCategory`)

#### Scenario: IntelliSense works in IDEs
- **WHEN** the user types `plugin.` in VSCode
- **THEN** all methods are listed with their parameter types and JSDoc descriptions derived from this spec
